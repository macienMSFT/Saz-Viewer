# SAZ Viewer

SAZ Viewer is a local command-line tool that reads Fiddler SAZ archives and writes a single portable HTML report. It has no runtime dependency on Fiddler Classic, FiddlerCore, a browser library, or a network service. Captured values are safely encoded or inserted as text nodes, and the report's Content Security Policy blocks network access and captured active content.

New to the codebase? Start with the [architecture guide](docs/architecture/README.md), which links component, data-flow, MAPI, browser-runtime, security, testing, and extension diagrams.

## Prerequisites

- Windows with the .NET 8 SDK or newer to build
- A current Microsoft Edge or Google Chrome release to open the generated report

## Build and test

```powershell
dotnet build .\SazViewer.sln
dotnet test .\SazViewer.sln
```

## Usage

```powershell
dotnet run --project .\SazViewer.Cli -- .\capture.saz
dotnet run --project .\SazViewer.Cli -- .\capture.saz .\reports\capture.html
dotnet run --project .\SazViewer.Cli -- --password-stdin .\encrypted.saz .\reports\encrypted.html
dotnet run --project .\SazViewer.Cli -- --scrub-auth .\capture.saz .\reports\shareable.html
dotnet run --project .\SazViewer.Cli -- --help
```

When no output path is supplied, the report is written beside the input archive with an `.html` extension.

Use `--scrub-auth` (or PowerShell-style `-ScrubAuth`) before sharing a report. It runs after HTTP, WebSocket, and MAPI parsing, replaces recognized credentials with typed markers such as `[REDACTED:Bearer]`, `[REDACTED:Cookie]`, and `[REDACTED:AzureSAS]`, and prints marker counts without printing secret values. It covers authentication and API-key headers, all cookie values, sensitive URL parameters, structured and plain-text bodies, WebSocket payloads, MAPI values, and report metadata. If compressed, binary, or otherwise opaque retained bytes cannot be rewritten safely, they are removed and the affected view shows a scrub-removal note. The compact report banner starts collapsed with the total replacement count; its accessible **Details** control reveals per-type counts. Expanded/collapsed state is safely persisted and synchronized across report tabs and inspector popups when browser storage is available, otherwise each load starts collapsed. Detection intentionally favors over-redaction, but the output should still be handled according to the capture's data classification.

Encrypted archives are detected automatically. In an interactive terminal, the tool prompts with `Password:` without echoing characters and allows up to three attempts. For automation, `--password-stdin` reads exactly one line, preserves meaningful leading/trailing spaces, accepts at most 1,024 characters, and does not retry. Supply that line from a trusted secret provider rather than a command-line argument, for example:

```powershell
Get-Secret -Name SazArchivePassword -AsPlainText |
  dotnet run --project .\SazViewer.Cli -- --password-stdin .\encrypted.saz
```

Do not use a literal password in `echo`, command arguments, scripts, or shell history. SAZ Viewer intentionally has no `--password <value>` option. .NET and the ZIP library ultimately require an immutable `string` for decryption, so the tool clears its mutable input buffers promptly but cannot guarantee complete password erasure from managed memory.

The HTTP session list uses **Time, ID, Result, Method, URL, Elapsed Time, Req, Resp** columns. Non-URL columns size to the widest value in the report while URL receives the remaining width and ellipsizes overflow. Result contains only the numeric HTTP status, or an em dash when no response was captured; the response reason/error remains available as a tooltip. Elapsed Time is Fiddler's Overall Elapsed (`ClientDoneResponse - ClientBeginRequest`) in integer milliseconds, or an em dash when either timer is missing, invalid, or reversed. Search includes Result and Elapsed Time as well as the existing method, URL, content type, endpoint, protocol, and WebSocket values. **Hide CONNECT** excludes CONNECT sessions case-insensitively and composes with text/status/protocol filters, Previous/Next navigation, and inspector-only popup state.

In the report, select an HTTP row with the mouse or keyboard to open a full-screen inspector dialog. The session table stays behind the dialog with its filter and scroll position preserved. The dialog shows Previous/Next controls that step through the currently visible/filtered rows in chronological order (disabled at the first/last row, plus an `Alt+Left`/`Alt+Right` shortcut), a position indicator, and an accessible Close control (also closable with `Escape`, which restores focus to the originating row). Each session has top-level Request and Response tabs, with Request selected first whenever the dialog opens or moves via Previous/Next. At 900 pixels and wider the inspector defaults to split Request/Response panes; below 900 pixels it defaults to the single-side view. The compact layout icon beside Previous/Next switches modes, and the redundant top-level Request/Response tabs are hidden while both panes are visible. Wide split panes are side by side with a pointer- and keyboard-resizable divider; narrow split panes stack vertically and disable the divider. Wide and narrow `single`/`split` choices are persisted independently through safely guarded `localStorage`, synchronized across open report tabs, and shared by main and inspector-only popup views. Crossing the 900-pixel breakpoint applies that width class's remembered choice or its default. During migration, a legacy `saz-viewer.http-layout.v1` value of `split` becomes the wide preference; legacy `single` is ignored so the new wide split default takes effect. When storage is unavailable, switching remains usable in the current page and each reload uses the width-class default. Within each visible side, a fixed-order tab strip — JSON, XML, MAPI, Image, WebView, HexView, Auth, Headers, Raw — fills the remaining space, with unavailable tabs shown disabled. Every available secondary view has a Copy control; JSON/XML copy their complete Pretty Text representation regardless of the active Tree/Pretty subview, MAPI copies a deterministic bounded text form of the complete retained protocol tree, and Headers/Raw preserve the report's bounded captured/decoded representation. Image is available only for a complete retained, structurally validated PNG, JPEG, GIF, WebP, BMP, or ICO body (never SVG), renders exclusively from a short-lived local Blob URL, and warns when the captured MIME disagrees with the validated byte signature. WebView is available only for complete retained HTML/XHTML-like text within the existing 64 KiB body limit. It reconstructs an inert structural document through a conservative client-side tokenizer and element allowlist that removes captured attributes, scripts, styles, forms, metadata, SVG/MathML, frames, and embedded resources, then renders it lazily in an opaque-origin iframe with an empty sandbox permission list and a deny-all internal CSP. The frame is removed on every view, side, session, popup, or inspector transition; its Source mode and active-view search use the original decoded source as text without weakening the sandbox. HexView formats the exact retained pre-decoding body bytes with offsets, 16-byte rows, and an ASCII gutter; when successful HTTP decoding produced distinct retained bytes, its compact source selector can switch to that decoded representation, with byte provenance and truncation labeled explicitly. Auth appears only for captured Authorization/Proxy-Authorization/WWW-Authenticate/Proxy-Authenticate headers, starts conservatively redacted, and requires an explicit per-view Reveal action before full values are displayed or copied; reveal state clears on every transition and is never persisted. Full captured header values remain present in Headers and Raw by design. Each visible pane has its own active-view search, which highlights case-insensitive literal matches only in that pane's current Tree/Pretty/Source subview, with wrapped Previous/Next and Enter/Shift+Enter navigation; searches are capped at 5,000 matches, remain independent in split view, and clear when their associated view, session, or inspector changes. Tree matches reveal collapsed JSON/XML/MAPI ancestors and Raw captured-byte details temporarily, restoring their exact prior state when the query clears or the view changes. JSON and XML tabs offer a default, initially expanded Tree view (individually togglable nodes, keyboard and mouse toggles) plus a Pretty Text syntax-highlighted view, when the body is recognized as valid JSON/XML; both views are rendered with bounded depth/child/node budgets so very large or deeply nested bodies stay responsive and show an accurate truncation note instead of expanding everything. Their compact **Expand all**, **Collapse all**, and **Copy** actions share one toolbar in that order; the expansion actions appear only in Tree mode and move focus to the selected view-mode button before hiding. JSON Tree shares the dense MAPI tree styling, including boxed `-`/`+` expanders, dotted guides, bold accent-colored names, monospace values, and `parent[index]` array labels; container count labels and bracket decorations are omitted. XML Tree retains its XML-specific element, attribute, and child-count presentation but uses the same contextual action-toolbar behavior. MAPI keeps its dedicated always-visible protocol-tree controls because it has no Pretty Text subview. The MAPI tab uses a dense, initially expanded, batched protocol tree with contained scrolling; parser kind and `@offset +length` metadata remain visible on every row, keyboard navigation follows ARIA tree conventions, valid text has control characters visibly escaped, and raw/non-printable nodes use a bounded labeled hex display. Headers shows only the captured header block; Raw shows the original captured headers plus the decoded body text (with decode status/encodings), a bounded hex view for binary bodies, and a compact "Captured bytes" control when pre-decode bytes are available. The initial secondary tab favors MAPI, then JSON/XML, then Raw, then Headers, whichever is available, and every tab strip supports Left/Right/Home/End keyboard navigation with roving focus. Detected MAPI/HTTP and NSPI sessions remain available through the protocol filter and search without a dedicated table column.

The table and inspector both provide a compact light-bulb theme button. With no saved choice, the report follows the operating-system light/dark preference and updates live; the first activation switches to the opposite theme, and later activations toggle Light/Dark. Explicit choices are persisted through safely guarded browser `localStorage` when available and synchronized across open report tabs. If a browser blocks storage for `file://` reports, switching still works in the current tab. To return to the system default, clear the report site's stored browser data; the compact control intentionally has no visible System mode.

If a session has associated `_w.txt` traffic, the same row opens a WebSocket inspector instead: chronological logical messages are listed on the left in compact **ID, Type, Body, Preview** columns and the selected message is shown on the right (stacked vertically on narrow screens). The desktop splitter supports pointer and keyboard resizing and remembers its ratio only while that report tab remains open. ID is the logical reassembled-message sequence, Body is the original logical payload byte count, and the one-line Preview is whitespace-normalized and explicitly ellipsized when bounded. The left-pane search filters case-insensitively against retained decoded text/JSON payload content only; binary data and any bytes omitted by safety truncation are not searched. The selected-payload search highlights bounded, case-insensitive literal matches in the active JSON Tree/Pretty, Text, or Raw view, with wrapped Previous/Next navigation; matching uses browser `toLowerCase()` behavior and is capped at 5,000 results. Client-to-server messages use a blue up arrow and accessible direction label; server-to-client messages use a green down arrow and label. Fragmented data messages are reassembled independently per direction while interleaved Ping, Pong, and Close frames stay visible. JSON, Text, and Raw tabs expose bounded safe views and Copy controls; Raw retains timestamps, fragmentation state, warnings, and underlying-frame IDs/metadata plus text or hex payload representation. Invalid, orphaned, unfinished, truncated, or unsupported frames remain visible with contextual warnings. Previous/Next may move between HTTP and WebSocket inspectors without changing the filtered table order. **Open in new tab** preserves the current filter and inspector type; after a successful handoff the original tab returns to the table, while a blocked popup leaves the original inspector open.

## Publish a self-contained Windows executable

```powershell
dotnet publish .\SazViewer.Cli\SazViewer.Cli.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o .\publish
.\publish\saz-viewer.exe .\capture.saz .\capture.html
```

Use `win-arm64` instead of `win-x64` for Windows on ARM. The published executable includes the .NET runtime; only the generated executable is required to run the tool.

## Capture handling

- SAZ files are treated as ZIP archives, and sparse `raw/<id>_*` entries are supported.
- Unencrypted ZIP/SAZ files use the .NET archive reader. Encrypted files support the format verified from Fiddler Everywhere Reporter exports: WinZip AES AE-2 with AES-256 and DEFLATE, including archives mixed with traditional PKZIP/ZipCrypto DEFLATE members and unencrypted members. Other AES vendor versions, key sizes, vendors, or encrypted compression methods fail with an explicit unsupported-encryption error rather than being guessed.
- WinZip AES members are fully read and their HMAC authentication code is verified before plaintext is passed to the parser. ZipCrypto members are also fully read and CRC-checked, but ZipCrypto is legacy encryption and does not provide modern authenticated-encryption security.
- ZipCrypto's password verifier is only one byte. In the rare case that an incorrect password passes that verifier, an interactive parse may consume another allowed attempt; if no supplied password succeeds, the tool preserves the integrity failure as archive corruption rather than claiming the password was definitely wrong.
- Encrypted extraction is memory-only and transactional. Safety limits are 100,000 archive entries, 256 MiB decompressed per encrypted entry, 1 GiB cumulative decrypted data, and a 1,000:1 declared compression ratio. A non-seekable input stream is copied only up to 512 MiB to enable central-directory validation.
- Individual missing or malformed records produce warnings instead of aborting the archive.
- Session-specific warnings remain visible in the affected session inspector. The aggregate warning section is currently omitted from generated HTML, while warning data remains available to the CLI/report model.
- HTTP body previews are bounded. Text uses a safely recognized charset; binary data is shown as a bounded hex preview.
- Declared chunked transfer framing is removed before content decoding. `gzip`, zlib-wrapped `deflate` (with a raw-DEFLATE compatibility fallback), and `br` are supported, including chained and repeated `Content-Encoding` fields in HTTP decoding order.
- Decoding is transactional and bounded: an HTTP entry is read through a 4 MiB protocol-payload limit plus bounded headers, each decoded stage is limited to at most 4 MiB and 100x expansion (with a 1 MiB floor), gzip content is capped at 128 members, displayed decoded bodies remain capped at 64 KiB, and captured encoded-byte views are capped at 16 KiB. Unsupported, corrupt, incomplete, or oversized content remains available as bounded captured hex with a warning.
- The inspector keeps captured headers unchanged. Successfully decoded bodies are shown as decoded text in the Raw tab (with decode status and removed encodings noted), and a compact "Captured bytes" control reveals the original pre-decode bytes when available.
- Each HTTP session has one versioned, bounded gzip envelope containing ordered request/response headers and retained captured bytes, plus decoded bytes only when they differ. Headers, Raw, JSON/XML formatting and trees, Auth redaction, Image, WebView, HexView, search text, and copy text are derived locally on demand rather than duplicated in the HTML. MAPI protocol trees and per-session WebSocket models remain independently compressed. HexView displays at most 1 KiB per captured/decoded representation and labels retained prefixes accurately; complete validated images and inert WebView source use the existing 64 KiB decoded presentation window, while incomplete bodies stay disabled. No payload is fetched from the network. Browsers without the required local `DecompressionStream` support show an actionable session error instead of a blank view.
- Without `--scrub-auth`, report generation is unchanged. With it, parsed model values are scrubbed before any HTML or compressed payload is serialized, including session-list URLs and bytes used by Raw, HexView, Image, WebView, Auth, search, and copy. Original compressed bytes are not retained when only decoded content can be safely rewritten.
- WebSocket records retain Fiddler ID/flags, direction, FIN/opcode/masking, lengths, timestamp, and warnings. Logical data messages are reassembled within explicit limits: 256 MiB uncompressed per `_w.txt` entry, 10,000 records, 16 MiB aggregate retained frame payload, 1 MiB retained per logical message, 5,000 displayed messages, and a 32 MiB decoded per-session report envelope. Limit hits remain visible as contextual warnings; there is intentionally no separate aggregate WebSocket section below the HTTP table.
- The tool does not execute captured content and does not make network requests.

The WebSocket reader follows the mixed pseudo-header/binary record layout [described by Fiddler's author](https://stackoverflow.com/a/29566732), accepts the leading blank-file-header and known synthetic-header variants, and decodes each declared-length frame according to [RFC 6455](https://datatracker.ietf.org/doc/html/rfc6455#section-5.2). Unknown or malformed variants are retained as bounded undecoded summaries with warnings.

Concatenated gzip members are supported. The raw-DEFLATE compatibility path has no format checksum, so it provides structural validation but cannot provide the integrity guarantee available for gzip and zlib-wrapped DEFLATE.

## MAPI/HTTP and NSPI inspection

MAPI parsing uses the fully normalized HTTP entity bytes, not the 64 KiB display preview. Detection is based on `application/mapi-http`, `X-RequestType`, and `X-ResponseCode`. Parser state and budgets are capture-local; payloads are capped at 4 MiB, protocol trees at 25,000 nodes and depth 64, collections at 100,000 items, strings at 1 MiB, and retained raw nodes at 16 KiB.

Implemented transport coverage includes all 23 `X-RequestType` request and response envelope schemas, response additional headers/status, mailbox and NSPI structures, all 32 property-value forms, all 12 restriction forms (including SubObject, which upstream omits from its dispatcher), all 11 rule-action types and payload layouts, all 572 PidTag, 365 PidLid, and 131 string-named upstream property symbols, chained MS-OXCRPC extended buffers, XOR `0xA5`, bounded Direct2/LZ77 decompression, ROP list/handle-table framing, all 132 upstream ROP names, and all 40 upstream auxiliary payload dispatch mappings plus MS-OXCRPC `AUX_TYPE_SERVER_CAPABILITIES`, and safe unknown/raw fallback. Individual ROP semantics cover all 128 request and all 131 response dispatcher cases: 49 request/50 response fixed-width schemas plus 79 request/81 response variable, self-contained decoders for the MS-OXCFOLD/MS-OXCTABL (folder/table), MS-OXCPRPT/MS-OXCSTOR (property/stream/store), MS-OXCMSG/MS-OXORULE/MS-OXCPERM/MS-OXCNOTIF (message/rule/permission/notification), and MS-OXCFXICS (FastTransfer/ICS) families, dispatched centrally per operation.

Capture-local FastTransfer state resolves each buffer-local handle index to a logical MAPI connection plus 32-bit server object handle, allowing bounded `varSizeValue` continuation across separate HTTP round trips while preventing joins across unrelated connections or reused handles. It tracks exact recursive marker pairs, classifies standalone ICS productions, and decodes context-special ProgressInformation and PropertyGroupInfo/PropertyGroup/GroupPropertyName structures, including bounded split values. Successful configuration ROPs select `contentsSync`, `hierarchySync`, `state`, `messageList`, and `topFolder` roots transactionally and validate their productions across buffers. Successful same-capture Folder/Message/Attachment handle provenance also selects markerless `folderContent`, `messageContent`, or `attachmentContent` roots for source CopyTo/CopyProperties and matching destination configurations, including same-Execute output-slot reuse; failed, missing, conflicting, or malformed provenance remains unvalidated rather than guessed. `messageList` enforces its optional DnPrefix/EcWarning/message entries and legal unmarked end-of-stream completion. Folder/message/attachment productions enforce recursive properties-before-messages-before-subfolders order, the exact two deletion-marker-delimited folder message lists plus optional trailing deletion marker before subfolders, message properties-before-recipients-before-attachments order, required attachment number where present, and embedded-message placement; the no-deleted-properties `topFolder` grammar continues to reject those folder deletion markers. RecoverMode `FXErrorInfo` unwinds to the nearest retained synchronization or message-list boundary and requires its single binary error property. Phase mismatches stop without speculative resynchronization, and download `Done` reports incomplete selected roots.

State is completed from authoritative download status and invalidated on failure, `RopRelease`, or successful handle reuse; upload status is retained but not interpreted because the protocol requires clients to ignore it. When multiple output-producing ROPs reuse one handle-table slot in a single HTTP session, intermediate handles are absent from the final table, so affected root/upload state is discarded explicitly instead of being attached to the wrong server object. ICS UploadStateStream Begin/Continue/End operations are correlated transactionally across HTTP round trips on the synchronization handle, bounded independently, and finalized as REPLGUID IDSET/CNSET data; failed, missing, mismatched, released, or reused operations discard state rather than splicing streams. Cross-operation shapes otherwise use bounded transactional state keyed by exact HTTP round trip or by logical MAPI connection as the protocol requires. MAPI/HTTP Session Context cookies provide the primary capture-local connection identity, including sequence-cookie rollover; Connect/Bind creates an isolated generation, ambiguous cookie matches isolate state instead of guessing, and a successful Disconnect/Unbind removes the connection's retained state and opaque cookie aliases. Lifecycle success requires a successful `X-ResponseCode` plus zero body `StatusCode`/`ErrorCode`; Connect/Bind also require their complete operation fields, while a truncated optional auxiliary suffix does not override an otherwise authoritative outcome. Cookie values are hashed for internal correlation and never emitted in diagnostics. This includes the five dispatcher shapes that require earlier request state, plus server-handle-keyed `RopSetColumns` reconstruction for `RopQueryRows`, `RopFindRow`, `RopExpandRow`, and `RopNotify` table rows; column state is committed only after success and invalidated on failure, `RopRelease`, `RopResetTable`, or table-handle reuse. RopLogon privacy is likewise committed only after a complete successful response, using the response flags as authoritative. Conflicting or unavailable correlation falls back to raw content plus a warning rather than guessing.

NSPI `PtypString8` values use the capture's declared code page; unsupported or unavailable code pages retain bounded raw bytes and mark the parse partial. Deterministically self-delimiting nested `PtypRestriction` and `PtypRuleAction` values are decoded in generic ROP and NSPI property paths; `PtypServerId` is decoded consistently in ROP, NSPI, and FastTransfer paths, while client-defined ServerId payloads remain bounded raw by definition. Multi-valued properties accept only the 12 element types for which MS-OXCDATA defines a multiple form; invalid combinations fail closed because their boundary cannot be determined safely. Rule-recipient AddressBookEntryIDs and ModLinkAtt permanent/ephemeral EntryIDs decode their exact bounded semantic fields, validate the required MUIDEMSAB provider where applicable, and fall back locally to raw on malformed content. Rule-action Folder/Message EntryIDs also expose their StoreObjectType name alongside the numeric value. Extended-rule EntryID sizes and recipient/property counts follow the 32-bit MS-OXORULE definitions, correcting narrower reads in the pinned upstream implementation. Auxiliary-buffer offset-referenced trailer strings/bytes are resolved from validated, bounds-checked offsets rather than upstream's unchecked sequential pointer arithmetic. Unknown generic property types and `RopReadRecipients` row properties without a deterministic column source remain explicit bounded raw fallback. Missing, malformed, mismatched, retried, and partially accepted state-changing operations are audited transactionally: uncertain outcomes invalidate the affected retained context, and queue mismatches discard later staged operations rather than shifting attribution. Differential validation includes the legal synthetic suite and a 1,172-session local corpus; Edge exercises compressed lazy MAPI rendering at the full 25,000-node parser budget, plus narrow and popup inspector modes. See [`docs/mapi-parity.json`](docs/mapi-parity.json) for exact counts and protocol-information limitations.
